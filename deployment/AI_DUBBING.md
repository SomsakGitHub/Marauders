# Optional AI dubbing into the viewer's language, with a shared server cache

The viewer explicitly chooses original or AI audio in their listening language (see "Listening language" below; the first version only produced Thai). Original playback never requests AI processing. The app checks for a reusable server audio file before creating a TranslationSession. A cache hit needs neither local speech permission nor translation models. On a miss, speech recognition, translation and narration in the listening language run on the viewer's iPhone.

Completed narration is compressed to AAC/M4A and uploaded to the existing R2 video bucket. Sharing is automatic, with an AI-translation label and original-audio choice; it does not claim endorsement by the clip owner. No paid AI provider, API key, new database table, Worker or bucket is required. Only the existing Worker is updated.

## Cache contract

- GET `/v1/videos/:id/dubbed-audio?source=<sha256-of-source-url>&lang=<code>` returns `missing` or `ready` plus an audio URL and the `language`. `lang` is one of the 22 listening languages (`ar da de en es fr hi id it ja ko nb nl pl pt ru sv th tr uk vi zh`, case-insensitive); anything else is a 400. Guests can read cached audio for public clips; a supplied invalid session is rejected. The original `/thai-audio` path is kept for app versions that predate listening languages and behaves as `lang=th`.
- POST the same path (with `lang`) requires a signed-in session, raw `audio/mp4` body, and `X-Source-SHA256`. Maximum: 4 MiB of structurally valid audio-only AAC with a positive finite duration; there is no fixed duration ceiling. Existing database-backed per-user rate limits apply.
- Immutable R2 key: `translations/<clip-id>/<source-url-sha256>-<lang>-v1.m4a` (Thai keeps its original `-th-v1` name, so existing objects remain valid). Each language is cached independently and never served for another language. Changed clip sources get a different key. Conditional `If-None-Match: *` writes preserve the first completed file when viewers upload concurrently.
- Successful clip deletion cleans all translation keys for that clip, in every language. Uploads recheck the source after writing to handle concurrent deletion or source changes.

The server validates MP4 box bounds, movie duration, audio handlers and AAC sample entries, not translation meaning. Two simultaneous first viewers can still both generate locally; once one upload completes, later viewers reuse it. Upload failure leaves local listening available. The upload retains bounded compressed data after the player closes, but terminating the app can interrupt an unfinished transfer.

## Local processing and limitations

Input: English, Spanish or Dutch speech, up to 12 MiB, with no fixed duration ceiling. For English and Spanish, audio is decoded incrementally to 16 kHz mono PCM WAV in 20-second segments, retaining only a segment-sized PCM buffer rather than the whole decoded clip. Digital silence is omitted. A no-speech segment does not discard words from earlier segments. If all segments are empty, original playback stays available. First use may require system language downloads and speech permission. Dutch is transcribed in one pass over the whole clip file by the Whisper model instead (see "Dutch"). Backgrounding cancels local processing; leaving or choosing original cleans local media.

The system voice for the listening language reads one combined translation. It does not preserve speaker identity, background audio or sentence timing. Dubbed playback restarts the video; longer narration is compressed to fit and shorter narration leaves silence. Words at segment boundaries can be imperfect.

## Verification

The exact Amsterdam clip produced about 22.6 seconds of Thai narration on iPhone 16 Pro Max. The uncached trial took about 75 seconds, including waiting for a no-speech segment. Backend checks cover shared reuse across sessions, concurrent conditional writes, source revisions, malformed/oversized/non-AAC audio and scoped deletion. iOS checks cover revision-bound URLs, authenticated upload, late-result cancellation and a cache hit without constructing a TranslationSession. The existing Worker was deployed and the real Amsterdam narration was uploaded through the signed-in iPhone session. A separate guest client downloaded the shared audio, verified its duration, and a fresh view model reused it without creating a TranslationSession (about 1.2 seconds for the measured lookup and media preparation). The first uncached conversion still has the longer local-processing cost. Temporary live probes are removed from the normal suite.

## Internal upload audio classification

The final exported MP4 is inspected on the iPhone before upload, off the main actor. Up to three one-second windows (start, middle, end) feed Apple's built-in SoundAnalysis classifier. A three-second sampling-work budget, cancellation, decoding failure or unsupported input returns an unknown advisory and never blocks upload. Classification is sampled evidence, not proof about the entire clip or a guarantee that recognition/translation will succeed. Speech and music can coexist. Singing/choir/rapping count as music evidence. Threshold policy: speech >= 0.5, mixed when music also >= 0.5; music only when music >= 0.7 and speech < 0.2; otherwise unknown. These are heuristic scores, not calibrated probabilities.

Language is a sanitized audio-track metadata hint, not language recognition. Missing metadata remains unknown. No speech permissions, downloaded translation models or paid AI calls are needed for classification. The existing 12-MiB local-translation size limit is advisory; duration alone is not a rejection condition; upload limits are unchanged. No diagnostic summary appears on the upload screen. Resetting/changing the selection discards stale results.

The upload sends optional `audioAssessment` JSON. The API bounds and validates fields, discards invalid advisory metadata without blocking upload, and stores the sanitized object in `feed_videos.audio_assessment` (migration 015). It stamps version/source/server receipt time; client-provided scores remain untrusted and must never authorize access or permanently deny translation. Legacy clips have NULL metadata. Feed/map/profile responses include the optional metadata. Shared Thai audio is still checked first; music classifications hide the AI audio entry points in feed and full-screen playback and suppress automatic Thai requests. Speech, mixed, unknown and legacy NULL metadata retain the viewer choice.

Dev inspection: Debug Log tab or Xcode console category `upload.audio-check` shows class, scores, language hint, sampled duration, elapsed time and trial limit. App logs keep 250 entries in RAM. For durable inspection use the existing database console:

```sql
SELECT id, created_at, audio_assessment
FROM feed_videos
ORDER BY created_at DESC
LIMIT 20;
```

Apply only `backend/sql/015_video_audio_assessment.sql` to an existing deployment before deploying the new Worker; do not rerun historical seed/purge migrations. No new external resources are required. Uploads from older app versions and clips uploaded before this feature remain NULL; no backfill is performed.

Physical iPhone verification: the real Amsterdam clip classified as mixed (speech score ~0.94, music ~0.66), sampled ~2.97 seconds, and took ~0.17 seconds after MP4 preparation. This single measurement is not an accuracy benchmark or a full upload-time measurement. Pure music and diverse noisy/multilingual clips still need broader manual evaluation. Backend tests cover metadata bounds, tamper sanitization, parameterized SQL and response round trip, alongside existing feed/auth/shared-audio checks. No test clip was published.

## Language detection (moved to the viewer's iPhone)

Upload no longer detects the spoken language. It used to run speech recognizers on the uploader's iPhone, which only covered the few languages that phone happened to have models for, asked the uploader for speech-recognition permission, and made every upload wait. The detection now runs on the **viewer's** iPhone, only when that viewer asks for AI audio and no saved audio exists, so most viewers never pay for it. Upload still classifies the audio (speech, music or mixed, via SoundAnalysis) because music-only clips offer no AI audio; that is not language detection.

What the viewer's iPhone does when the clip does not declare its language (new uploads never do; see "Clips that declare a language") and it has not been detected on this phone before:

1. Look for saved AI audio in the viewer's language (a hit needs no detection, no permission and no models).
2. If the **language detection model** is not on the iPhone, the player asks "Download the language detection model?", naming the size (about 150 MB), that it comes from Hugging Face and that Wi-Fi is better. "Download" starts the preparation of that one clip with the download allowed; the agreement is not stored anywhere, so it can never start a download later on another clip. A download that is already running (started from Settings or another player) is joined without asking. If the app goes to the background while the question is open, the question is closed. "Not now" is remembered for the rest of the session, and the limited detection of step 5 is used. The question returns the next time the app starts.
3. Download the clip (bounded to 12 MiB) and pick the windows to listen to from the first five minutes of its audio: up to two stretches of at most 20 seconds each (one when the model is missing), chosen by how many of their seconds are loud enough to be speech (`SpeechWindowSelector`, loudness per second against a floor and against a tenth of the clip's loud level). A clip whose opening already holds speech keeps its opening; a later window replaces it only when it holds at least 3 more speech seconds (any speech at all, when the opening has fewer than 3). The second window is the best stretch that does not overlap the first and has at least 3 speech seconds; one shorter than 5 seconds is not used, because it says too little about the language to overrule the first. Loudness cannot tell speech from music, so a loud music bed can still win; the audio assessment from upload is what keeps music-only clips out.
4. **With the model:** it listens to each window and names a language, with no speech-recognition permission. The windows it could read must name the same language, the mean probability must reach 0.8, and the label must be one of the 42 languages the app names (Norwegian `no` and `nn` both become `nb`). A clip short enough for a single window is accepted on that window alone. The answer is acted on, and remembered for the clip only when the mean probability is at least 0.95, so a doubtful label cannot hide the audio button for good. When the model is unsure or the windows disagree, the recognizers of step 5 get a turn; if permission is denied then, the result is "could not tell".
5. **Without the model (or when it was unsure, or when its download failed):** ask for speech-recognition permission, then recognize the first (best) window as English and Spanish (the dubbing sources that have a quick recognizer; Dutch is not tried, see "Dutch") and, when it is one of the ten languages that have a recognizer (German, English, Spanish, French, Italian, Japanese, Korean, Portuguese, Thai, Chinese), as the viewer's own language, and check what language the transcript really reads as (NaturalLanguage). A recognizer forced onto the wrong language produces gibberish that fails this check, so it yields no evidence rather than a confident wrong answer. A transcript counts only when the recognizer was reasonably sure (confidence at least 0.45), the text has at least 12 letters and reads as the requested language with at least 0.8 confidence; the evidence score is the smaller of the two. Languages whose models are already installed go first, all at once; if the best result reaches 0.8 it is accepted. Otherwise the remaining languages get a turn, which may download a speech model once, so an English clip never makes a phone fetch a Spanish model. If two different languages end within 0.15 of each other the result is ambiguous and nothing is chosen. The viewer's own language, which the app cannot dub from, has to reach 0.65 on its own, because a recognizer forced onto a close relative (German on a Dutch clip scored 0.51) produces believable text at middling confidence. 0.65 is a heuristic between that one measurement and the confidence real speech reaches. If the download failed and the recognizers find nothing, the player reports the download problem (offline, no free storage, or a model that would not load) instead of "could not tell". A clip that declares no language is therefore dubbed from Dutch only after the detection model is installed; without it the result is "could not tell".
6. The answer is remembered on that phone for the clip (a local list capped at 300 clips, stored under `detectedClipLanguages.v2`; answers made by the previous detector were discarded when this key was introduced). If it equals the viewer's language the player says the clip is already in it and keeps the original audio, and the audio button stops being offered for that clip. If it is a language the app cannot dub from yet, the player says so (for example Russian). If nothing is clear, the player says it could not tell, and without the model it points to Settings › Language models.

The clip's audio, its transcript and the detected language are not uploaded and nothing about the detection is stored on the server (the `audioAssessment.spokenLanguage` field is only present on clips uploaded by older builds, see below). The finished AI voice is uploaded for other viewers to reuse, as described under "Cache contract". The per-clip memo is not shared between viewers, so each phone detects a clip once; sharing it through the server would need a write path with the same first-write-wins trust problem as the audio cache.

### The language detection model

An acoustic language identifier: Whisper base converted for Core ML, run through WhisperKit 1.1.1 (an exact SwiftPM version, linked to the app target). It hears a window and names one of about 99 languages, instead of needing a speech recognizer per language. The same model writes down Dutch speech for dubbing (see "Dutch").

- **Where it comes from.** Hugging Face, when the viewer agrees or taps Download in Settings › Language models: `argmaxinc/whisperkit-coreml` at commit `0f63a7800b00dd0226abd051b906c246e1907482` (folder `openai_whisper-base`, about 147 MB) and the three tokenizer files of `openai/whisper-base` at commit `e37978b90ca9030d5170a5c07aadb050351a65bb` (about 3 MB). Both commits are pinned in `LanguageDetectionModelStore.Release.current`, so the weights cannot change under the app and the thresholds below stay valid. During the download huggingface.co and the CDN hosts it redirects to (`*.hf.co`) see the phone's IP address and the app's user agent. It is a new network host for the app; mirroring the files on the Worker would remove it but is not done. There is no Wi-Fi-only rule: the alert asks the viewer, and says Wi-Fi is better.
- **Where it lives.** `Application Support/LanguageDetection/<first 8 characters of the model commit>-<first 8 of the tokenizer commit>/`, marked as excluded from backups. A marker file is written last, so a download that stopped halfway never counts as installed. After downloading, the install checks that the tokenizer loads from disk (WhisperKit would otherwise go back to Hugging Face and the unpinned main branch) and lets Core ML prepare the model for this chip once, which takes most of the time after the download. If preparing fails the files stay, so a retry does not download again; a download that does not match the pinned files is deleted. A build that pins other revisions starts a new folder and deletes the old ones. Remove it by swiping the row in Settings. After a failed install the row offers Remove until it is refreshed; files left by a failed preparation are reused by the next Download.
- **The download outlives the player.** It belongs to the store: leaving the player does not stop a download the viewer agreed to, a second request joins the running one, and a caller that is cancelled stops waiting at once. Removing the model stops a running install first.
- **Offline.** Once installed, finding the language needs no network: the app loads the model and tokenizer from those folders with downloads switched off. Verified on a physical iPhone with every Hugging Face request pointed at a dead address.
- **Cost.** Measured on an iPhone 16 Pro Max (iOS 26.7.1, debug build): about 63 s for the first install (download plus preparation), about 9 s to load the model in a freshly launched app, about 0.9 s to load it again after it was unloaded, and about 0.1 s per window once loaded. One shared instance keeps the model for 20 seconds after the last check and then unloads it to release memory. Core ML may repeat the preparation after an iOS update.
- **How well it works.** The measurements come from the throwaway branch `spike/language-id` (commit `2daedd0`, not merged) and are not reproducible from `main`. On the real Dutch clip both windows were named `nl` with a mean probability of 0.99. On synthetic speech (the system voice of each of the 22 listening languages, one short dialogue each, clean and with mild noise) it was right 22 of 22 clean and 21 of 22 noisy, scoring `zh` and `yue` both as Chinese and `no` and `nn` both as Norwegian; the miss was Norwegian read as Turkish with probability 0.24, which the 0.8 threshold rejects. That is thin evidence: one real clip, one voice per language and mild noise. The 0.8 threshold is a first guess, not a calibration, and noisy Dutch already scored 0.835. Confusion between close languages (for example Danish, Norwegian and Swedish, or Spanish and Portuguese) was not studied. The tiny model (77 MB) was not chosen because its probabilities separate right from wrong badly (a wrong answer at 0.75, right ones as low as 0.36).
- **Limits.** A confidently wrong label (0.95 or more, for example Catalan or Portuguese for a Spanish clip) is acted on and remembered, and nothing cross-checks it with the recognizers. A second window of 5 seconds or more that is music or noise must still agree with the first. The model cannot say "no speech": music or noise that is not digital silence still gets a language. Clips classified as music at upload never offer AI audio, but the classification is only a hint, so a clip with a long music intro can still get a wrong label. Only the first two windows are heard. WhisperKit reports only the winner's probability, so there is no runner-up or margin. A detected language the app cannot dub from only produces the "not supported yet" message; dubbing from it needs a speech engine for that language. The same Whisper model transcribes Dutch (see "Dutch").
- **Not checked.** Whether the question still appears when the answer arrives while the audio-choice dialog is closing, and the release binary for WhisperKit's microphone-permission symbols.
- **Not done.** Warming the model before the viewer taps (the first check in a fresh launch waits about 9 s), a Wi-Fi-only rule, a free-space check before downloading, and licence notices for WhisperKit (MIT), its vendored Hub and tokenizer code (Apache-2.0) and the model weights. The app also still has no `PrivacyInfo.xcprivacy`.

## Duration ceiling removed

The former 120-second input gate and whole-PCM allocation ceiling are removed. Audio preparation flushes each 20-second segment to disk while decoding; it does not accumulate the entire clip in RAM. The 12-MiB compressed input limit remains, as does the per-segment recognition timeout for English and Spanish (the Dutch route has none, see "Dutch"). Cache encoding and server structural validation no longer impose the previous 180-second audio duration ceiling; the 4-MiB cached audio size bound is unchanged. Older `exceedsTranslationLimit=true` metadata may reflect the former duration policy and is not a playback/translation gate.

A physical-device trial using the actual 141.3-second latest clip decoded seven non-silent chunks and returned a Thai narration file in about 6.9 seconds. The generated narration was about 5.1 seconds; this validates removal of the duration rejection and successful generation, not transcription completeness or translation quality for the entire source. No narration was uploaded during that diagnostic. The permanent normalization test covers 141 seconds and verifies total decoded duration and per-chunk bounds. Backend tests accept longer positive finite durations while retaining bounded AAC validation.

## Speech recognition for Spanish (and other analyzer languages)

The legacy `SFSpeechRecognizer` on the test iPhone did not support offline Spanish, so Spanish uses iOS 26 `SpeechTranscriber` / `SpeechAnalyzer` (shared `SpeechAnalyzerTranscriber`). It verifies device and locale support and reuses installed assets; a missing model is downloaded only when the caller allows it (the viewer asked for AI audio, or detection ran out of installed options). The analyzer has a watchdog (12 seconds for a detection sample, 60 seconds per dubbing segment). Physical-device check: Spanish text was recognized from synthesized speech in about 0.3 seconds with a heuristic confidence of about 0.9. Audio and text stay on the device. Apple lets an app keep only 5 reserved speech languages ("Too many allocated locales, 5 maximum"); on the test phone the app held de-DE, en-US, es-ES, ja-JP and nl-NL, some of them taken by the recognizers language detection tries, so a sixth language (Thai) could not be reserved and the player and Settings say the limit was reached.

## Language model downloads (Settings)

The Settings tab lists on-device models with install state and a download button: Translation pairs (each dubbing source into the viewer's listening languages), speech-recognition locales (English, Thai, Spanish) and the language detection model described above, which also transcribes Dutch. Translation downloads use Apple's system prompt and can only be removed in iOS Settings; speech models show progress and can be removed with a swipe. If the English → Thai pair is missing when the user chooses Thai dubbing, the playback message says a one-time download is needed and points here, and dubbing continues once the system download finishes.

## Spanish → Thai dubbing

_Thai was the first and only target; it is now one of 22 listening languages (see the last section), and everything below applies to the chosen language._

The dubbing source language comes from, in order: the language an older clip declares in `audioAssessment.spokenLanguage` (the uploader's choice or an upload-time guess from earlier builds), what this iPhone detected for the clip earlier, or a detection run now (see "Language detection"). English transcribes with the legacy on-device recognizer; Spanish transcribes each 20-second segment with `SpeechAnalyzer` (shared `SpeechAnalyzerTranscriber`, 60-second per-segment watchdog); Dutch with the Whisper model over the whole clip at once (see "Dutch"); then Apple Translation into the listening language and the system voice. Because the viewer explicitly asked for AI audio, the first Spanish run may download the Spanish speech model and the translation pair; both can be installed ahead of time from Settings → Language models. Cached audio is per (clip, language), independent of the source language, so viewers reuse it regardless of how the source was found.

Limits: English, Spanish and Dutch are routed as sources (see "Dutch" below). A clip known or detected to be in any other language keeps the original audio and the player says dubbing from it is not supported yet. Translation quality for Spanish was not evaluated beyond a synthesized-speech transcription check on a physical iPhone.

### Dutch

Dutch is dubbed from with the **Whisper base model** that also names a clip's language (`WhisperEngine.transcribe`), on the phone like the other sources. It replaces the iOS 26 `DictationTranscriber`, which was built first and heard only about half of the test clip (below). The model is the language detection model (about 150 MB from Hugging Face, see "The language detection model"); there is no separate Dutch download.

- **How it is asked for.** A clip detected as Dutch has the model already, because detection needs it. A clip that declares or remembers Dutch while the model is missing asks first: "Download the Dutch speech model?", naming about 150 MB, Hugging Face and Wi-Fi. "Download" downloads it inside the preparation, with progress in the status line ("Downloading the Dutch speech model… 40%", then "Preparing the language detection model on this iPhone…"). A download that is already running is joined without asking, "Not now" keeps the original audio and says why, and a failed download names the speech model.
- **No speech permission.** The model runs inside the app, so dubbing from Dutch does not ask for speech-recognition permission (Apple's recognizers, used for English and Spanish, still do).
- **One pass over the whole clip.** The clip file goes to WhisperKit in one call (incremental loading, so memory stays bounded) and WhisperKit decides where to cut: audio longer than 30 seconds is split at a quiet moment, and cut hard at 30 seconds only when none is found, so a cut inside a word is still possible. The fixed 20-second windows the other sources use were tried first and do not work here: the second window of the test clip starts in the middle of a word, and a greedy pass on it ended at once with nothing in 10 of 10 runs, while WhisperKit's retries at higher temperatures (which sample at random) recovered the text in some runs and returned an empty window in others (5 of 8 in one measurement). Handing over the whole file gave the same text in every run (89 to 91 words depending on the loading mode; 3 runs per setting, with and without retries), and the same clip repeated to 120 and 200 seconds gave 272 to 274 and 454 to 455 words where the repeats ideally hold 267 and 445, in both loading modes (2 runs each). That is one clip repeated, not different speech.
- **Cleaning.** `AcousticTranscriptPolicy` removes what the model writes for noise, music and silence, because it always writes something. Labels for sounds in brackets, stars or parentheses ("[BLANK_AUDIO]", "* Musik *", "(Applaus)", "（音楽）") go, innermost first and at most 60 characters long, with the speech around them kept; a parenthetical remark in real speech goes with them, which is accepted. A segment with a music note (♪ ♫ ♬ 🎵) is dropped whole. Subtitle credits and sign-offs go sentence by sentence, so a credit stuck to a sentence of speech takes only itself: a list of markers in Dutch, German, French, Spanish, Portuguese, Italian, Russian, Ukrainian, Polish, Turkish, Swedish, Danish, Norwegian, Arabic, Chinese, Japanese, Korean, Vietnamese and Indonesian, "(C)" at the start of a sentence, and a sentence of capital letters with a four-digit year ("TV GELDERLAND 2021."). The markers are substrings, so a person who talks about subtitles loses that sentence. Of the markers, only the Dutch broadcaster, the Russian credit and the Vietnamese sign-off were seen in measurements; the rest are the families Whisper models are widely reported to write and were not seen here. It also drops loops (compression ratio above 2.4) and removes control tokens and a dash stuck to the first word of a new speaker's turn. The result must then read as Dutch to NaturalLanguage (from 12 letters on, at 0.6 or more) with a mean token probability of at least 0.4, or the clip is reported as unclear speech and nothing is cached.
- **How well the cleaning works.** Measured on an iPhone by feeding the same Whisper output to the earlier rules and to these, for the 22-language dialogue read by system voices (1 or 2 voices per language): clean speech came out identical (27 of 27); with pink noise 10 dB below the speech, 10 of 27 transcripts changed, none got worse, and the mean character error fell from 22.5% to 20.3% (the English ones lost "[BLANK_AUDIO]", Russian lost "Редактор субтитров …", Vietnamese its sign-off, Dutch "TV GELDERLAND 2020."); with a different noise at 5 dB and 3 seconds of noise after the speech, 13 changed and 2 were an entire transcript that was only a label, which is now empty. Fed 8 seconds of nothing but noise, a synthetic chord, or near silence, with the language forced to each of the 22, the earlier rules passed text on in 54 of 66 cases (labels, credits, invented phrases) and these in 5 of 66: invented phrases that read like speech ("Đi thôi, đi thôi!", Swedish and Arabic sentences). The same measurement run twice differed a little (51 against 54 of 66 for the earlier rules), because WhisperKit's retries sample at random. The rules were written from the outputs of the first sweep (clean speech and noise at 10 dB), so the 10 dB numbers only check cases already seen; the 5 dB noise with a longer tail and the noise-only, chord and near-silence inputs were not seen when the rules were written. Not caught, by design or for lack of a rule: a stock closing the model writes for silence ("Thank you.", "ご視聴ありがとうございました", "ขอบคุณครับ", "¡Adiós!"), because a person says those too.
- **Not caught.** WhisperKit 1.1.1 reports no no-speech probability (it is fixed at 0), its other scores are per decoding window, and its mean probability includes the forced prompt tokens, so it flatters short texts and the confidence is not a quality gate: a Norwegian transcript with half its characters wrong passed at 0.45. The music tail of the test clip was written with higher confidence than its speech. The sweep used synthetic voices and one noise type; real music, speech in the background and clips of minutes were not measured.
- **Measured on the test clip**, a vendor and a customer at a market stall: about 17 short turns and 89 words in Whisper small's transcript, which Whisper base's structure matches (neither is a human reference).
  - Whisper base on the clip file heard 90 words and 12 of 12 turn markers (words or phrases from both halves of the conversation), with word errors such as "als te blieft" for "alsjeblieft" and "pimpas" for "pinpas".
  - The `DictationTranscriber` route this replaces heard about 43 words and dropped whole turns. More volume did not bring them back, and 5-second and 3-second pieces recovered only part (about 53 and 66 words) with words split at the cuts. That route, its level boost and its Settings row were removed.
  - Through `DubbingViewModel.request` (opt-in device test `DutchDubbingDeviceTests`, enabled with `RUN_DEVICE_DUBBING_TEST`; Dutch into English, clip fetched beforehand, nothing uploaded, speech permission refused on purpose, Apple Translation's default strategy hosted in a test window) the English voice is 34.8 seconds long, from a translation that covers the whole conversation; the dictation route gave 13.8 seconds. The request took 4.5 seconds with the model just loaded for the first check (a freshly launched app adds about 9 seconds to load it, and a warm transcription of the clip takes about 1.4 seconds). Cancelling the task 0.3 seconds into a run that takes 1.4 seconds stopped it there with a cancellation error.
  - Not run: the player view itself, and Dutch into Thai, which needs Apple's one-time download of that translation pair and asks the viewer to confirm.
- **Limits.** The base model makes word errors, and they reach the translation. It was tested on one clip. It writes something for any audio it is told is Dutch, so the plausibility check above is what stands between a wrong detection and a nonsense voice. There is no timeout and no progress count for the Dutch transcription (Apple's engines keep their 60-second limit per window), only the status line "Transcribing Dutch speech on this iPhone…", and the first run after launching the app waits about 9 seconds more for the model. When the retries sample at random the text can differ between runs on audio the first pass finds hard. A model that fails to run is reported as a failure to translate on this iPhone, not as unclear speech. The Thai voice already cached for this clip (18.5 seconds) came from the dictation route and is served as is, because the cache is first-write-wins and nothing replaces it.

## Clips that declare a language (older builds)

New uploads never carry a language. The uploader's side has no need to name or detect it, so the upload screen has no language row; it briefly had an optional "Language in clip" picker, which was removed. Clips uploaded by earlier builds can still carry `audioAssessment.spokenLanguage`: either the uploader's choice (`status=confirmed`, `method=uploader`) or a `likely` language guessed on the uploader's phone before detection moved to the viewer. The app treats both as a declared language, which skips detection on every viewer's phone (no permission prompt, no download).

The API still accepts those shapes so older app versions keep working: `confirmed` needs a valid code and a client-supplied confidence is dropped, and the older `uploader_unsure` reason is accepted too. Like the rest of the assessment this is untrusted advisory metadata: it only selects the dubbing source language and never authorizes anything. A declared language we cannot dub from yet (anything but English, Spanish and Dutch) means the audio button is not offered for that clip. Stored JSONB needs no migration.

## Listening language (viewer's language)

The goal is that a viewer can hear any clip in a language they understand, so the target is the viewer's, not a fixed Thai.

- **Choosing it.** Settings → Listening language lists the 22 languages Apple Translation can produce that also have a system speech voice; rows this iPhone cannot serve are disabled. "Automatic" (the default) uses the device's language list in order, skipping the language already spoken in the clip: a viewer who lists English then Thai hears Thai dubbing of an English clip and English dubbing of a Spanish clip. An explicit choice is stored in `UserDefaults` and always wins, except that a clip already spoken in that language is not dubbed. The audio-choice dialog also has "Change listening language…", which opens the same list and starts dubbing as soon as a language is chosen.
- **Entry points.** The feed's "Choose audio" button and the full-screen player's audio button appear when the clip has speech and dubbing could change what the viewer hears: its language is unknown (the viewer's iPhone will find out when asked), or known, supported and different from at least one language the viewer listens in. They are hidden for music, for a clip already in the viewer's language (declared, or detected earlier on this phone) and for a declared language we cannot dub from yet. A viewer whose device languages are all unsupported still gets the button, so they can choose a language. The dialog lists one "Listen in …" button per language the viewer listens in (except the clip's own), so for a clip of unknown language the viewer picks the target explicitly.
- **Pipeline.** Saved audio, else source language (declared on an older clip, remembered from an earlier detection, or detected now; English, Spanish or Dutch for now) → Apple Translation into the listening language → the best installed system voice for that language (usual region first, then quality; novelty voices are skipped) → AAC upload to `dubbed-audio?lang=<code>`. If translation has no route between the two languages or no voice is installed, the player says so and keeps the original audio.
- **Language models.** Settings → Language models lists the translation pairs the viewer may need (each dubbing source into each possible listening language), not a fixed Thai pair.
- **Interface language.** Dubbing and settings text is localized (English and Thai; Thai is the only extra region in `Localizable.xcstrings`). Language names inside sentences follow the app's interface language rather than the region setting, so a sentence never mixes a third language. Other languages fall back to English.
- **Known gaps.** Source languages beyond English, Spanish and Dutch are not routed yet (Whisper writes down about 99 languages, so each is one case to add, with the model's accuracy for that language checked on a real clip). Without the language detection model, detection can only name English, Spanish and, for ten of the listening languages, the viewer's own language; with it, 42 languages are named but dubbing from most of them is still not supported. Detection takes a few seconds plus the clip download on a cache miss (and about 9 s more to load the model in a freshly launched app), and treats the first speech stretches as representative (a music intro can defeat it). Chinese uses one entry (Mandarin) for both scripts. The cache is still first-write-wins for any signed-in viewer, so a bad upload would be heard by later viewers of that language; there is no report/removal flow yet.
