# ADR-012: Force update: a minimum build read from Firebase Remote Config

**Status:** Accepted (built, tested, and proved on the simulator against the owner's Firebase project on 2026-11-22; no TestFlight build holds the gate yet, see *Consequences*)  
**Date:** 2026-11-21  
**Scope:** in the app `UpdateDecision`, `CheckUpdateRequirementUseCase`, `FirebaseAppConfigRepository`, `FirebaseRemoteConfigSource`, `FirebasePlistCheck`, `UpdateGateViewModel`, `UpdateRequiredView`, `UpdateGateComposition` and the gate in `MaraudersApp`; around it the plist's hand-off (`Scripts/check-firebase-plist.sh`, the `build` and `beta` lanes, the `Jenkinsfile`, `.gitignore`) and the two parameters in the Firebase console.

## Context

A gate only stops builds that already contain it, and no build does yet, so it has to ship in the next build, before it is needed. The Worker already carries compatibility code for old builds by hand (`/v1/feed` keeps `viewerID`, `/v1/map/clips` stays for installed apps); a minimum build is how that code gets retired one piece at a time. A TestFlight build waits for the owner to start Jenkins, so the minimum has to change without one. The build number is Jenkins' `BUILD_NUMBER`, handed to the build as `CURRENT_PROJECT_VERSION` (so `CFBundleVersion`) only when it is set: every other build, a Run from Xcode included, is build 1, and `MARKETING_VERSION` is a constant 1.0.

## Decision

- **The key is the build number.** An update is required only when all of these hold, checked in this order, and otherwise the app runs: there is a config; its `minimumBuild` is above 0; its link is `https` on `apple.com` or a subdomain (no credentials, no port); this build's `CFBundleVersion` is digits; the build is not `DEBUG`; and it is below the minimum (equal is allowed). Only `DEBUG` is exempt, so a Run of the Staging scheme is never blocked, while a local Release build (a Run of the Production scheme, an archive made by hand) is build 1 and is stopped like any other by a minimum above 1. Build 1 was exempt too until 2026-11-22, when the owner took the exemption out so that a Production-scheme Run on a device shows the screen without a change to the build number.
- **The two numbers come from Firebase Remote Config.** The owner publishes `minimum_build` (Number; 0 or empty means no gate) and `update_url` (String, the Update button's link) in the Firebase console. The app reads both as text and parses the minimum with `BuildNumber.parse`, the rule it applies to its own build number: digits only, spaces and line breaks around them ignored. So "12o", "1.5", "-3", "+5", a number too large for an `Int`, an empty value and an absent parameter all count as 0, which is "no gate"; the app sets no in-app defaults. Nothing upstream checks what the console holds, so `UpdateDecision` is the only check of the link: one that is not `https` on `apple.com` blocks nobody. A typo can lift the gate or set it too high; no code can tell the second from a wish, and the undo is publishing 0.
- **One file imports Firebase.** `FirebaseRemoteConfigSource` is the only one (a script test fails when another does); everything else sees the two texts as `RemoteConfigValues` through `RemoteConfigSource`, and `FirebaseAppConfigRepository` turns them into the answer. The SDK is `firebase-ios-sdk`, "up to next major" from 13.2.0, products `FirebaseCore` and `FirebaseRemoteConfig` only: no Analytics, so no ATT prompt and no audience conditions. `minimumFetchInterval` is 3600 s, not the SDK's 12 hours, which would carry a raise to devices too slowly (it still caps a device at one real fetch an hour however often the app opens), and `fetchTimeout` is 10 s, not 60, so that a hung fetch frees the gate's one in-flight slot sooner. Inside that hour the SDK answers from the values it saved and asks Google nothing, and both ways end in a success, so a log line that only said `config refreshed: minimumBuild=5` could not tell Google's answer from a saved one (the owner read a saved 5 as fresh on 2026-11-22, after publishing 0). The source therefore reads the SDK's `lastFetchTime` before and after `fetchAndActivate()`, which moves only when Google answered, and the line says which: `(from Google)`, or `(from the SDK's saved values, Google last asked <age> ago)`.
- **The SDK starts at the first ask, never at launch.** `MaraudersApp` asks only after the pass check, a UI test never builds the source (the `UITEST` composition picks `UITestAppConfigRepository`), and `fetch()` is `@concurrent`, so the plist read, its check and the wait for the network run off the main actor. The one call that starts the SDK is made on the main actor, because the SDK's header asks for that ("This method should be called from the main thread", `FIRApp.h`) and its failure is the one Swift cannot catch: once per launch, and about 35 ms in the simulator from the `decision:` line to the SDK's first log line.
- **A bad plist means "gate open", never a crash.** The SDK raises Objective-C exceptions, which Swift cannot catch, while it starts: Core when there is no plist or its `GOOGLE_APP_ID` is missing or not of the shape `1:<project number>:ios:<hex>`, Installations when its `API_KEY` is not 39 characters (an `A`, then letters, digits, `-` and `_`) or its `PROJECT_ID` is missing, and Remote Config when its `GCM_SENDER_ID` is missing (read in the SDK's source, 13.2.0). `FirebasePlistCheck` applies those four rules to the bundled `GoogleService-Info.plist` before the SDK sees it (the first version read the app id only, and the first run with a fixture plist crashed the app on its placeholder key), and without a usable plist the source logs one line, which names the key and never holds its value, and answers nil, so the app runs as it did before the gate. The source keeps whether it has started the SDK itself and never asks the SDK, because every question put to the SDK while no app is configured logs an error line of its own. What the check cannot see is another app's plist, which the SDK only logs, so the TestFlight lane guards that (next bullet).
- **The plist is not in git.** The repository is public, so `Marauders-ios/Marauders/GoogleService-Info.plist` is git-ignored. Jenkins hands it over as the file credential `marauders-firebase-plist` (`FIREBASE_PLIST_PATH`, bound in the Deploy stage), the `build` lane copies it into place, and the `beta` lane runs `Scripts/check-firebase-plist.sh` first and stops before it builds when the file is missing, is not a plist, has a `BUNDLE_ID` other than `com.somsak.Marauders` or holds a `GOOGLE_APP_ID`, `API_KEY`, `PROJECT_ID` or `GCM_SENDER_ID` that fails the four rules above (the script and `FirebasePlistCheck` are two copies of one rule, each with its own tests and none that compares them: change both together). No scheme and not the Production guard change, so an Xcode Run with no plist still builds and runs.
- **Fail open, never wait.** The app keeps the last good answer in UserDefaults (`update.appConfig.v1`) and decides from it at launch, synchronously: a known "required" shows at once, and a build that knows nothing is never blocked. One refresh runs at launch and one at each foreground, at most one per 10 minutes and never two at once (a clock moved back counts as long enough ago). Only an answer counts: a fetch that failed, timed out or was cancelled leaves the kept answer as it was, and one that succeeded replaces it, a minimum of 0 included, so a lowered or cleared minimum lifts the screen without a relaunch.
- **A screen gate only.** `UpdateRequiredView` replaces `AppRootView` in `MaraudersApp.body`, inside the client-key check, with no dismiss and no "later". The upload session and the location monitor are process-wide singletons that `MaraudersApp` starts before any view exists and that reach the Worker on their own, so the screen stops neither (read in `BackgroundClipUploader.launch()`, `awaitSystemEvents()` and `BackgroundLocationMonitor.resume()` on 2026-11-21); the Worker stays the authority on what an old build may do. The one link to the screen's world, `connectUploaderRejections`, only ends a session on a rejected token and waits until `AppRootView` is back.
- **Under `UITEST`** the gate is off and never touches the network or Firebase; three launch arguments next to `UITEST` give it an answer (`UITestUpdateScenario`, `UITestAppConfigRepository`, build 2, a fixed link): `UITEST_UPDATE_REQUIRED` keeps a "required" from the start, and `UITEST_UPDATE_REQUIRED_AFTER_REFRESH` and `UITEST_UPDATE_LIFTED_AFTER_REFRESH` start from "nothing kept" and from "required kept" and change it 10 s after the launch, which is how two UI tests watch the window swap by itself, in both directions.
- **Rollout rule.** Raise the minimum only when build N can be installed from TestFlight (later the App Store), and never above the newest uploaded build: publish `minimum_build` = N and `update_url` in the console. To undo, publish 0: no commit, no deploy and no rollback. Either reaches a device within about an hour, once the app is launched or comes to the foreground.

## Alternatives

- **A first-party route on the Worker (`GET /v1/config`, answering from two `wrangler.toml` vars).** Built and tested on 2026-11-21, never deployed or committed, and replaced before it shipped because the owner chose Firebase Remote Config: raising the minimum becomes a button in a console instead of a commit and a guarded deploy, and the console is where later flags would go. It was the smaller design: no SDK, no plist, no Google host, no new App Privacy answers, every change reviewed in a commit, and a raise reaching devices within about 10 minutes. The work is kept as a patch and copies in the owner's working folder, `.superpowers/sdd/kept-worker-config-route/`, which is not in git.
- **The Worker answers `426` to old builds.** Enforced by the server with no cache, but no build sends its number in a header of its own, the screen would appear only after a call failed, and the error would have to cross Data to Presentation. Kept as a later server-side backstop.
- **Ask the App Store which version is current (iTunes lookup).** It needs a public listing, does not work for TestFlight and cannot set a minimum.
- **Commit the plist.** Smaller still: no credential, no lane check, no missing-plist case. Not chosen: the repository is public, and a Google API key in a public file draws secret-scanning alerts and puts the project's identifiers in the open, even though Google documents such keys as identifiers rather than secrets (not re-checked).
- **Keep build 1 exempt and add a launch argument that forces the screen.** The first version of the rule exempted build 1 (the number of every local build) so that the owner's own Run could never be blocked, and the option proposed on 2026-11-22, when the owner wanted to see the screen on a device from Xcode, was a launch argument that makes a Run show it whatever the minimum is. Not chosen: the owner chose to take the build-1 exemption out instead, which leaves one rule and no switch, and accepts known limit (12).

## Consequences

- **Rollout, each step the owner's:** a Firebase project with Google Analytics off, an iOS app `com.somsak.Marauders`, the downloaded `GoogleService-Info.plist`, and the parameters `minimum_build` (Number, 0) and `update_url` (String, empty), published; the file credential `marauders-firebase-plist` in Jenkins; the App Store Connect privacy answers before a build goes beyond the owner's own devices (the SDK's own manifests declare "Other Diagnostic Data" collected and no tracking; the answers are the owner's); commits and a push; a TestFlight build that holds the gate (read `CFBundleVersion` and the plist's `BUNDLE_ID` back from the `.ipa`, as `docs/ci-cd.md` does); and only when needed, publish a minimum with the Update link the owner gives (TestFlight now, the App Store later).
- **Known limits.** (1) A build without the gate cannot be stopped, and none has it until the next TestFlight build. (2) The Update button opening the link and the TestFlight path itself are first proved by the first TestFlight build that holds the gate. (3) The 10-minute throttle uses the device clock. (4) Someone already inside the app when the minimum is raised meets the screen at the next foreground, not at once. (5) A console edit has no review, test or commit, and the rule in the app is the only guard: a link off `apple.com` blocks nobody, and a minimum set too high blocks everyone until it is undone. (6) A raise or an undo reaches a device once the SDK's hour has passed and the app is launched or foregrounded; a real-time listener would shorten it and is not built. Until then the log shows the earlier number marked `(from the SDK's saved values, …)`, which tells a saved value from a console that was not changed; deleting the app clears the saved values at once, so a fresh install asks Google. (7) A build that cannot reach Firebase, or has no usable plist, keeps what it knows: one that already holds "required" stays stopped. (8) Staging and Production share one bundle id, one Firebase app and one kept answer, so both read the same values (as both schemes use one backend today). (9) The first build after this change resolves and compiles Firebase (slow once, about 1.4 GB of package clones); after that a Run with no plist behaves as before, and one with the plist asks Firebase and logs `config refreshed: minimumBuild=<n> (<where it came from>)`. (10) Remote Config values are not private: nothing confidential goes in the console's two parameters. (11) The unit-test host is the real app, so with a plist in the source tree every unit-test run also starts the SDK and asks Firebase once (a plist the guard turns away is only logged); a fixture plist belongs outside the tree, except for a proof build. (12) A local Release build is build 1 and is stopped like any other: while a `minimum_build` above 1 is published, a Run of the Production scheme from Xcode, or an archive made by hand, shows the Update screen (a Run of the Staging scheme never does, being `DEBUG`); publish 0 before running Production on a device for other work, and use Staging for daily work.
- **Tests.** In the app `UpdateDecisionTests`, `BuildNumberTests`, `CheckUpdateRequirementUseCaseTests`, `FirebaseAppConfigRepositoryTests` (the parse table, the entry written only on success, a failed or cancelled fetch leaving the old one, an unreadable entry removed), `FirebasePlistCheckTests` (the four keys: a bad or missing value of each, a value that is not text, the file read, and a reason that never holds the file's values), `UpdateGateViewModelTests`, `UpdateGateCompositionTests`, `UITestUpdateScenarioTests` and six UI tests of the screen (the swap in both directions included); `check-firebase-plist-tests.sh` for the lane's plist check (the same four keys, `BUNDLE_ID`, the usage errors, and that it prints no value of the file); and in `backend/test/scripts` `firebasePlistInjection.test.mjs` (the one importer, the two products, the source never asking the SDK whether it is started and starting it on the main actor, the `.gitignore` line, both lanes, the Fastfile's plist helper run in Ruby on a read-only credential copied twice, the Jenkins binding, these docs, and the CI workflow watching the files these pins read) and `clientKeyInjection.test.mjs` (the window's shape, and the refresh behind the pass).

## Triggers to revisit

- A second value joins the answer (a kill switch, a flag): decide whether it stays a Remote Config parameter, and whether it needs conditions or a real-time listener.
- A raise must reach devices faster than an hour: add the real-time listener, or lower `minimumFetchInterval` within what Google's throttle allows.
- Builds that ignore the screen need a server-side backstop: add the `426` of *Alternatives*, which needs a header the builds do not send yet.
- Staging gets its own bundle id or backend: the kept answer's key and the Firebase app become per environment.
- Another Firebase product, Analytics included, joins: the App Privacy answers, the ATT question and the "two products only" pin change with it.
- `firebase-ios-sdk` moves to another version (`Package.resolved`): read `FIRApp.m`, `FIRInstallations.m` and `FIRRemoteConfigComponent.m` again for new places that raise, because the plist guard and the start on the main actor were checked against 13.2.0 only.

## Evidence

Read on 2026-11-21 and 2026-11-22 with Xcode 27.2 on the iOS 27.2 simulator, before anything was committed.

- **Suites.** Unit target (`MaraudersTests`, scheme Marauders Staging): 1464 tests in 147 suites passed. UI target (`MaraudersUITests`): 90 tests, 89 passed and one failed, the known simulator-only `testACommentInAnotherLanguageGivesThePageASwitchAndNoButtonOfItsOwn` (it fails at HEAD too), so `xcodebuild` exits 65 (1599 s in all; run again on the finished tree after the final review's fix pass with the same counts as the 1447 s run before it); the six UI tests of the Update screen, the swap in both directions included, are among the 89. Backend `npm test` (every runner) passed and `npm run test:scripts` 147 of 147 (it runs the Fastfile's own plist helper in Ruby); the four shell suites under `Marauders-ios/Scripts/tests` 44, 31, 27 and 33 cases; `check-layers.sh --strict` exit 0; `find-plain-strings.py` OK; swift-format reports only an older LineLength warning at `AccountDeletionAPIClientTests.swift:44`, a file this change does not touch.
- **Production archives** (scheme Marauders Production, generic iOS, unsigned): `** ARCHIVE SUCCEEDED **` without a plist (none inside the `.app`, and the Production guard passes, so a build with no plist still builds) and with one in the tree (bundled in the `.app`).
- **The guard on the real app** (Staging, a fresh install each time, the app's log read with `simctl spawn … log show`): (a) no plist: no crash; `gate:` and `decision: allowed` come first, then `firebase not started: no usable GoogleService-Info.plist; the gate stays open` and `config refresh failed`; nothing of Firebase is logged before `gate:`, and the one line that mentions Firebase is the app's own, so the SDK writes none. (b) A plist with a well-formed app id and the placeholder `FIXTURE-NOT-A-KEY` as API key, which the first version of the guard let through and which crashed the app (an uncaught `com.firebase.installations` exception from `validateAPIKey`; the same file in the source tree crashed the unit-test host): now no crash and `firebase not started: API_KEY is missing or malformed; the gate stays open`. (c) A plist of valid shape (a project that does not exist): the SDK starts at the first ask and not before, the fetch fails harmlessly (`firebase fetch failed: com.google.remoteconfig.ErrorDomain 8003`, then `config refresh failed`) and the gate stays open. All three runs were repeated after the final review moved the SDK's start onto the main actor: no crash report in any of them, the same lines in the same order, and in (c) the SDK starts about 35 ms after the `decision:` line. `check-firebase-plist.sh` prints `firebase plist ok: com.somsak.Marauders` for the plist of (c) and names API_KEY for the one of (b).
- **Against the owner's Firebase project** (Task 9, step 1; 2026-11-22, on the simulator, a fresh install with the owner's plist bundled): Staging (build 1) logs `gate: build=1 debug=true`, `decision: allowed` and, about 1.2 s after the SDK started, `config refreshed: minimumBuild=0`; Production (Release-Production, `CURRENT_PROJECT_VERSION=2`) logs `gate: build=2 debug=false` and the same two lines; the app went on to sign in and load its feed, the SDK wrote one line (`I-RCN000072`, a new config database) and no error, and no crash report was written. A simulator build made without entitlements (`CODE_SIGNING_ALLOWED=NO`) cannot reach the Keychain, so the SDK's Installations failed (`-34018`), the fetch ended in `ErrorDomain 8003` and the gate stayed open with the app running: the fail-open path met a real failure. A 0 does not show by itself that the two parameters are published (a missing parameter reads as 0 too); step 2 does.
- **Against the owner's Firebase project, with a published minimum** (Task 9, step 2; 2026-11-22, on the simulator): the owner published `minimum_build` = 5 and an apple.com `update_url`. Production build 2 (Release-Production, signed for the simulator with its entitlements, the owner's plist bundled), freshly installed, logged `gate: build=2 debug=false` and `decision: allowed`, then `config refreshed: minimumBuild=5` and `decision: required`, and the Update screen (the title "Update required", its one-sentence body and the Update button) replaced the app. So both parameters are published and read, and step 1's 0 was a real 0 and not a missing parameter. The SDK wrote its one `I-RCN000072` line and no crash report was written. Tapping Update opened Safari on the published link (an apple.com page, its address ending `/testflight/id…`; the simulator has no App Store); the status bar's "Marauders" link took the tester back, and the Update screen was still there: the button does not lift the gate.
- **Against the owner's Firebase project, with the minimum published as 0 again** (Task 9, step 3; 2026-11-22, on the simulator): the owner published `minimum_build` = 0 again (the `update_url` stayed). A fresh install of the same Production build 2 logged `gate: build=2 debug=false` and `decision: allowed`, then `config refreshed: minimumBuild=0` 1.3 s later, and no `decision: required` anywhere (the live `log stream` and the `log show` taken afterwards agree), and the app ran as before: a screenshot shows the Feed with a clip and the tab bar, with no Update screen. No crash report was written. So the owner's project answered 0, 5 and 0 on one build, and the gate decided allowed, required and allowed, each as the rule says.
- **Build 1 no longer exempt** (2026-11-22, the change that lets a Production-scheme Run show the screen at build 1). Each new pin was watched failing first: with the old rule `onlyABuildBelowTheMinimumMustUpdate` (build 1 against minimum 5), `aBuildNumberedOneIsStoppedLikeAnyOther`, `theKeptAnswerIsJudgedByThisBuild` and `aLocalReleaseBuildNumberedOneIsStoppedByTheKeptAnswer` failed (4 issues in 3 suites), while the pins of what stays exempt (a `DEBUG` build numbered 1 or 9, build 1 against a minimum of 1) passed; after `currentBuild != 1` was taken out of `UpdateDecision.decide` the same 22 tests passed. Whole unit target 1465 tests in 147 suites passed (1464 before; the one new test is the composition's), `npm run test:scripts` 147 of 147, `check-layers.sh --strict` exit 0, `find-plain-strings.py` OK, swift-format clean on the six changed Swift files, and the six UI tests of the Update screen passed again (62.6 s; they run as build 2 under `UITEST`, so the change cannot reach them, and they were run to prove it). Against the owner's Firebase project with `minimum_build` = 5 published, on the simulator: Production (Release-Production, signed for the simulator, `CURRENT_PROJECT_VERSION=1`, `CFBundleVersion` read back as 1 from the built app, a fresh install, the owner's plist bundled) logged `gate: build=1 debug=false` and `decision: allowed`, then `config refreshed: minimumBuild=5` 1.4 s later and `decision: required`, and the Update screen replaced the app (screenshot seen); no crash report was written.
- **The log says where the answer came from** (2026-11-22, after the owner read a saved `minimumBuild=5` as a fresh one). Each new pin was watched failing first: the script test `theSourceSaysWhetherGoogleWasAskedOrTheSdkAnsweredFromItsSavedValues` (the source reads `lastFetchTime` before and after `fetchAndActivate()`, and the repository's line carries the origin), and, against a stub, the 15 issues of `RemoteConfigOriginTests` (the verdict of the two times, the age text) and the 2 of `theLogSaysWhereTheAnswerCameFrom` (the line of a source that cannot tell stays as it was and passed at once); after the change all 17 passed. Whole unit target 1472 tests in 148 suites passed (1465 in 147 before), `npm run test:scripts` 148 of 148, `check-layers.sh --strict` exit 0, `find-plain-strings.py` OK (the two age literals are in the allowlist: a log line no viewer reads), swift-format clean. The UI target was not re-run: nothing it reaches changed (the UITEST composition builds neither the SDK source nor this repository). Against the owner's Firebase project, with `minimum_build` = 0 published, on the simulator, Release-Production build 1 (`CFBundleVersion` read back as 1, the owner's plist bundled): a fresh install logged `config refreshed: minimumBuild=0 (from Google)` 1.4 s after `decision: allowed`; the same install, terminated and launched again 28 s later without a reinstall, logged `config refreshed: minimumBuild=0 (from the SDK's saved values, Google last asked 26 s ago)` 56 ms after the launch, with no SDK line at all; with the SDK's saved last-fetch time moved back by two hours in the app's container (the simulator shut down and booted first, because a first try without that restart still read the cached old time and said `1 min ago`), the next launch logged `(from Google)` and the saved time was 26 s old afterwards; one more launch logged `(from the SDK's saved values, Google last asked 28 s ago)`. So all three verdicts were met with the real SDK: never asked, asked long ago, asked a moment ago. No crash report was written. The case `last ask unknown` (a success with no saved time) is covered by the unit pins only, because the SDK does not produce it.
- **Not proved yet:** the Update screen lifting on the same install without a reinstall (the unit tests and the two UI tests that watch the swap in both directions cover it with fakes; live it needs the SDK's hour to pass, `minimumFetchInterval = 3600`, which is why step 3 used a fresh install); how an iPhone with the App Store handles the link (the simulator opened Safari); and the first TestFlight build that holds the gate, read back from the `.ipa` (the plist's `BUNDLE_ID` and `CFBundleVersion`), which also proves the Jenkins path (the plist credential).
