# ADR-011: Account deletion: Apple first, then the files, then the rows

**Status:** Accepted (built and tested; not deployed yet, see *Consequences*)  
**Date:** 2026-11-20  
**Scope:** `DELETE /v1/users/me` (`backend/src/routes/deleteAccount.ts`, `backend/src/auth/appleClient.ts`, `backend/src/db/accountDeletion.ts`, `backend/src/storage/clipObjects.ts`), the Worker secrets `APPLE_TEAM_ID`, `APPLE_KEY_ID` and `APPLE_PRIVATE_KEY`, and in the app Settings' Delete Account row, `DeleteAccountSheet`, `AccountDeletionViewModel`, `DeleteAccountUseCase`, `AccountDeletionAPIClient`, `AuthViewModel.finishAccountDeletion()` and the removal of the saved feed

## Context

The app lets a person sign up with Apple and keep clips, comments, likes, follows and a shared location, but gave no way to leave: Sign Out only clears the phone, and `DELETE /v1/videos/:id` removes one clip. App Store Review Guideline 5.1.1(v) requires an app that creates accounts to let people delete them inside the app, and Apple asks apps that offer Sign in with Apple to revoke the person's tokens when the account goes (otherwise Marauders stays listed under Sign in with Apple in their Apple ID settings).

Two facts of the data decide the design. The database cascades almost everything from `app_users` and `feed_videos`, but `feed_videos.owner_user_id` has no `ON DELETE` clause (`NO ACTION`), so a person's row cannot go while one of their clips is left. And a clip is not always one R2 object: a clip converted with `npm run video:hls` is a playlist, its segments and the original upload under the same uuid, served without authentication, so anything left behind stays public.

## Decision

- **One request, in a fixed order.** `DELETE /v1/users/me` with `{ "authorizationCode" }` runs: authenticate, the `account-delete` rate limit (5 an hour per user), the body, the user row (none: 204, and a code that came with the request is revoked at Apple, best effort; see *An account that is already gone*), the clips (more than `MAX_CLIPS_PER_DELETION`: 409 with the limit, nothing touched), Apple, R2, then one SQL statement. From Apple on, the work runs under `ctx.waitUntil` and the response awaits the same promise, so a client that goes away cannot cut a deletion in half. No migration, no queue, no cron, no new dependency (`jose` already signs and verifies).
- **Apple first, the rows last: the invariant.** The user row is deleted only after Apple was told, so a missing row means a revoked grant (the one grant a retry can make afterwards is revoked best effort: *An account that is already gone*, Known limit 10), and an Apple outage during the deletion can never leave a person "deleted" but still linked. R2 sits between them because it is idempotent and the rows still say what to retry; the rows go last because they are the index a retry works from. Every step is safe to repeat; each R2 call and the final statement are attempted three times, 150 ms apart.
- **An account that is already gone** (a retry after a lost 204, or a device that was still signed in) answers 204 and deletes nothing. A code that comes with that request is another Apple confirmation, and the first run revoked the earlier grant, so that confirmation made a new one that nothing else would revoke: it would sit in the person's Apple ID settings with no account behind it, the "deleted but still linked" state this design exists to prevent. So, after the answer and under `ctx.waitUntil`, the Worker exchanges the code and revokes the refresh token. No `sub` is compared (the grant belongs to whoever confirmed on the sheet, and revoking it touches no account), nothing changes the answer (a failure is only logged, as a step name) and the person never waits for Apple. A test account sends no code, and a Worker without the Apple secrets does nothing. The first design answered 204 and called no one; the final review of this branch found the gap.
- **Apple confirms the person.** The sheet asks Sign in with Apple (`SignInWithAppleButton(.continue)`, no scopes). Its one-time `authorizationCode` goes to the Worker, which signs a client secret (ES256; header `kid` = key id; `iss` = team id; `sub` = client id `APPLE_CLIENT_ID`; `aud` = `https://appleid.apple.com`; `exp` 300 s after `iat`), exchanges the code at `POST https://appleid.apple.com/auth/token`, verifies the returned `id_token` with the existing `verifyAppleIdentityToken`, compares its `sub` with the stored `apple_sub` (another Apple ID: 403 and nothing is deleted) and revokes the refresh token at `POST https://appleid.apple.com/auth/revoke`. `invalid_grant` on the exchange is 400, `invalid_client` 503, a network error or a 5xx 502, and a missing secret 503 before any call. A `dev:` test account (the debug sign-in makes them) has no Apple grant and skips Apple.
- **One SQL statement:** `WITH deleted_clips AS (DELETE FROM feed_videos WHERE owner_user_id = $1 RETURNING id) DELETE FROM app_users WHERE id = $1;`. It deletes by `owner_user_id`, not by the ids read earlier, so a clip added from another device in between cannot make the delete fail. Everything else cascades.
- **R2 by prefix, but only for a clean key.** The uuid comes from the key in `stream_url`, never from the clip id. A key of the exact form `videos/<36-character lowercase uuid>/…` is deleted by the prefix `videos/<uuid>` (a uuid has a fixed length, so the prefix cannot reach another clip); every other key is deleted exactly, and a key with `..` or a backslash is skipped. The avatar object and each clip's dubbed audio (`translations/<clip id>/`) go too.
- **A cap on clips per request.** `MAX_CLIPS_PER_DELETION` (15 until the owner says which Cloudflare plan the Worker is on) bounds the subrequests one deletion makes. A person over it gets "delete some from your Profile first".
- **Three optional Worker secrets:** `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` (the `.p8` text, real newlines or `\n` escapes). Without them the route answers 503 for an Apple account and the app says deletion is not available. Their values never appear in the repository, a log line, a response or a fixture; the tests generate keys at run time.
- **In the app.** Settings has an Account section, only for a signed-in viewer, with a destructive Delete Account row. `ContentView` presents the sheet from its own state, because the row goes with the session and the confirmation has to outlive it. The sheet says what goes, asks Apple, shows the progress where the button was (Cancel and the swipe are off meanwhile) and ends with "Your account was deleted" and Done. A cancelled Apple sheet returns to the first screen; every other failure is a message in the person's words (`AccountDeletionError`) above the button, which can be tapped again; a double tap and an Apple answer that arrives while a deletion runs are ignored.
- **On 204** `AuthViewModel.finishAccountDeletion()` is the local half of a sign out and nothing else (no Worker call: the rows are gone): it drops the pending upload, clears the Keychain session and both tokens and sets `isSignedIn = false`, which makes `ContentView` reset the profile, feed, likes, follows and friend locations and switches the background location monitor off. `DeleteAccountUseCase` removes the feed this iPhone saved right after the Worker answered (`SessionFeedStartupCache.removeAll()`): the whole `Caches/PersonalFeedStartup-v2` folder, with every account's and the guest's copies of clips, the caches that are open first so they refuse new files from then on. A deletion that failed keeps the saved feed for the next try.
- **Debug aids.** A Staging build in UI-test mode has a plain button in place of Apple's (Apple's sheet cannot be driven by a test), and one signed in as a Simulator test user has "Delete test user", which sends no code. Both are `Text(verbatim:)`, listed in `plain-strings-allowlist.txt` and in the Debug-only guard of `LocalizationCatalogTests`. A Production build has neither.

## Alternatives

- **A resumable deletion** (a `deletion_requests` table and a retry job or a queue). It would remove the clip cap and the "a retry needs one more Apple confirmation" limit, at the price of a migration, a cron or queue and state to reason about. Not worth it for a first release: the cap and the retry are visible and recoverable.
- **Revoke last and tolerate a failed revoke.** No sign-out surprise after a half-finished deletion (Known limit 3), but an Apple outage would leave a deleted person still linked in their Apple ID settings, and a crash between the last two steps would leave that unnoticed. The chosen order keeps the invariant and shrinks the window with retries and `waitUntil` instead of changing `restoreSession`.
- **A grace period** (mark the account, delete after some days). Kinder to a mistaken tap, but the owner chose immediate deletion, and a marked account would still be linked to Apple.
- **Anonymise instead of delete.** The comments a person wrote on other people's clips go with the account (the cascade does it for free) rather than staying under a blank name.
- **Delete without revoking** and tell people to remove the app in their Apple ID settings. Apple asks for the revocation, it is the part of the guideline most likely to be checked in review, and the Apple ID would keep listing the app.
- **No Apple sheet; revoke with a stored token.** The Worker keeps no Apple refresh token (sign-in only verifies the identity token), and the sheet is also the proof that the person holding the phone owns the account.
- **No Apple call when the row is already gone** (the first design). Simplest, but a retry after a lost 204 would leave the grant its own confirmation made, and the sheet would say "Your account was deleted" over it.

## Consequences

- **Rollout, each step the owner's:** create the Sign in with Apple key in the developer portal (`deployment/README.md`) and set the three secrets on production (`wrangler secret put`, the key from a file on stdin); read Cloudflare's current subrequest limit for the Worker's plan and set the cap; merge; deploy with `npm run deploy:production -- --confirm production` (no migration; rollback is `wrangler rollback`, after which the route answers 405 and the app shows "not available"); check A on the Simulator as a `dev:` user with test clips; check B on a phone with a real Apple ID, then look in the iPhone's Apple ID settings; only then a TestFlight build. Until the secrets are set the route answers 503 for every Apple account, which App Review would meet.
- **What a failure leaves behind.** Apple failing: nothing deleted. R2 failing after three attempts: Apple revoked, some files gone, every row intact, so the person's clips exist but do not play. The statement failing three times: the same. Each is retried from the sheet with a new Apple confirmation, because a code is single-use and valid for five minutes. A response lost after the statement leaves everything gone, and the same request answers 204 (and revokes the grant its own Apple confirmation made).
- **Known limits.**
  1. A person over the cap deletes some clips from Profile first.
  2. A retry after a failure that came after Apple was told needs one more Apple confirmation, because no state is kept between attempts.
  3. A failure after Apple was told (R2 or the database failing three times in a row) leaves the account with some or all of its files gone, so clips do not play and the last location may still show. The person can retry at once from the sheet. If they leave it, the app can sign them out on its own: the account still exists, but the next time the app asks Apple about the saved session (a relaunch, or opening Profile, Map or Upload) Apple reports the credential revoked and `restoreSession` signs the person out locally, as it does for any revoked credential. Signing in again with the same Apple ID reaches the same account, and Delete Account works again. The app cannot tell this failure from an Apple-side one (both are 502), and `restoreSession` is not changed for it.
  4. A clip uploaded from another device during the few seconds of a deletion can leave an R2 object with no row.
  5. Other devices of the person stay signed in until their next like, follow, comment or friend-locations request, which answers 401 for the missing user (at the latest when the access token expires and the refresh fails). A token minted before the deletion cannot write anything meanwhile: every write needs the user row. Signing in again with the same Apple ID creates a new, empty account.
  6. Dubbed audio the person uploaded for other people's clips stays: it is a shared machine translation and its id no longer points to anyone.
  7. Viewers who already loaded one of the person's clips keep playing their cached copy until it is evicted.
  8. Neon and Cloudflare keep backups and internal copies on their own schedules. The privacy policy (a separate piece of work) has to say that deletion from backups follows the providers' schedules. Not checked for the owner's plans.
  9. A revoke that Apple answers 200 to without doing it cannot be seen from the Worker; only check B proves it.
  10. The revoke for an account that is already gone is best effort. If Apple is unreachable or refuses at that moment the answer is still 204 and the grant the retry made stays in the person's Apple ID settings until they remove it; the Worker logs `account deletion: could not revoke the grant of an account that was already deleted (<kind>)`. Limit 9 applies here too.
- **Found while building.** The Worker's calls to Apple have no timeout of their own (the app gives up after 60 s, and the Worker finishes the deletion under `waitUntil` anyway). The tests run `jose`'s Node build while the deployed Worker bundles its web build, so only check B proves the signing end to end. `Caches/FeedStartup-v1`, the default folder of an older build's startup cache, is not removed (nothing reads it). `DELETE /v1/videos/:id` still removes only the key in `stream_url`, so a clip converted to HLS leaves its segments and original public: a separate decision, not part of this change.
- **Tests.** `npm run test:account-deletion` runs the Worker's suites alone (the Apple client, the R2 plan, the statement on a fake Neon, the handler and the router), and `npm test` runs them with everything else. The app has unit tests for the API client, the use case, the saved feed's removal, `finishAccountDeletion`, the view model and the container's wiring, UI tests for the row, the sheet and both outcomes, and the accessibility audit of the sheet.

## Evidence

- **Postgres:** a one-off PGlite run (PostgreSQL 18.3 under PGlite 0.5.8, all 23 files of `backend/sql` applied in name order, nothing committed) showed that the one statement deletes a person with clips, comments, likes, reports, follows both ways and refresh tokens while a second person's own rows stay intact; that a person with no clips deletes cleanly and an unknown id or a repeat deletes zero rows; and, as a control, that `DELETE FROM app_users` alone fails with SQLSTATE 23503 on `feed_videos_owner_user_id_fkey`. The two-statement fallback was not needed.
- **`waitUntil`:** Cloudflare's runtime documentation (read on 2026-11-20) says work given to `ctx.waitUntil()` can run up to 30 seconds after the response is sent or the client disconnects, shared by all `waitUntil` calls of the request. A deletion takes a few seconds.
- **Apple:** the documented endpoints, form fields (`client_id`, `client_secret`, `code`, `grant_type=authorization_code`; `token`, `token_type_hint=refresh_token`), response fields (`id_token`, `refresh_token`), error codes and client-secret claims were read on 2026-11-20 and match the above. `redirect_uri` is left out: the native flow does not send one.
- **Not proved by any test:** that a `DELETE` with a JSON body survives URLSession, Cloudflare and the Worker (a stripped body would answer 400; check A is the proof, and the fallback would be `POST /v1/users/me/delete`, a change to the route, the router, the API client and their tests); that Apple accepts the signed client secret and that the grant is revoked (Known limit 9); the branch of the sheet that takes the code out of a real `ASAuthorizationAppleIDCredential` (a test cannot build one); and that authorizing again after a revoke makes a new grant that Apple ID settings list again, the premise of the revoke for an account that is already gone (Apple's documented behaviour; the last step of check B, signing in again, shows Marauders back in the list). Check B covers the last three.

## Triggers to revisit

- A person reports the clip cap (the 409), or deletions that fail after Apple was told more than once: build the resumable deletion of *Alternatives* (state kept between attempts, a retry that needs no new Apple confirmation), and lift the cap.
- The Worker's Cloudflare plan changes, or its subrequest limit does: recompute `MAX_CLIPS_PER_DELETION` (the plan's R1 step) before any other change.
- Review or a user finds a grant still listed in Apple ID settings after a deletion that answered 204: the revoke is the first suspect (Known limit 9); read the Worker's `account deletion: could not …` lines.
- The app gets another way to sign in, or accounts that are not tied to one Apple ID: the order "Apple first" needs a new answer for them.
- A migration adds a table that refers to `app_users` or `feed_videos` without `ON DELETE CASCADE` (report and block are likely to): the one statement then fails with 23503 and every deletion answers 500. Repeat the Postgres proof above with the new table before it ships.
